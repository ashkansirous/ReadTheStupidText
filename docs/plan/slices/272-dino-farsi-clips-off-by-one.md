# Slice 272 — Dino: Farsi pre-made audio falls back to the device voice after the first animal sound

*In progress 2026-11-05 (user: "fix the farsi books").* Bug fix, Dino Reader, content and tooling (the app code is unchanged). Reported by the user on 2026-11-05: in Lion and Mouse in Farsi, from page 5 ("but you are too small", where the lion lifts his paw) the read falls back to the device voice and stays on it; English was fine.

**Touches:** `content/dino/{goldilocks,lion-and-mouse,little-red-hen,red-riding-hood,three-little-pigs,tortoise-and-hare,town-mouse-country-mouse,ugly-duckling}/audio/fa/**`, the same eight books' `audio-cast.json` (`audioPacks.fa`), `tools/premade-audio/**`, `tools/DinoReader.BookBuilder/**`, `.github/workflows/dino-store.yml`, `.github/workflows/tools-selftests.yml`, `.github/CLAUDE.md`, `src/DinoReader.Core/PremadeAudio.cs`, `src/DinoReader.App/StoryVoicing.cs` (counting rule moved to Core, no behaviour change), `src/DinoReader.App/Testing/DinoTestCommands.cs` (Debug hook), `.maestro/dino/premade-audio-past-roar.yaml`, `docs/plan/slices/272-dino-farsi-clips-off-by-one.md`.

## Cause (shown by a scan, 2026-11-05)

- The app finds a clip by the piece's position and checks the manifest's text hash at that position (`src/DinoReader.Core/PremadeAudio.cs` `ClipAt`). A wrong hash means the device voice reads that piece.
- The Farsi clips were recorded on 2026-11-03 with the animal sound words (e.g. `غرررر!`, the lion's roar) counted as spoken pieces. Slice 255 (ffd09cc0, merged 2026-11-04 02:40Z) made the app play a real recording for them and leave them out of the count (`StoryVoicing.cs` `WithAnimalSounds`, `SentenceDump.cs`). From the first sound word on, every Farsi piece's position is one (or more) off, its hash misses, and the rest of the book is read by the device voice.
- The other 14 languages were recorded after 04:15Z that day (Slice 246 D3), with sound words already left out, so they line up. (Timing read from the wave ledger and PR merge times, not from the clip files: likely, not proven.)
- Scan of origin/main 07d00d4b: 16 books x 15 languages = 240 manifests, 232 line up, 8 do not, all Farsi. Extra entries / first bad position: goldilocks 5/51, lion-and-mouse 6/19, little-red-hen 14/16, red-riding-hood 3/21, three-little-pigs 7/24, tortoise-and-hare 1/33, town-mouse-country-mouse 8/20, ugly-duckling 6/12. The only difference in all 8 is the sound-word entries; no text was edited or re-split. Record: `D:/ReadTheStupidText-worktrees/reviews/lion-fa/scan.md` (copy the table into this file when building).

Not fixed here: live goldilocks book version 12 vs repo `book.json` 11.

**Why no check caught it:** nothing compares a pack's manifest with the sentences the current app reads. Slice 255 changed the count and every pack built before it silently stopped fitting.

**What analytics showed** (`dino_usage`, 2026-11-03 to 2026-11-05): `read_voice` for lion-and-mouse fa was `premade` twice and `device:clip_missing` once (23:34Z, Android 1.106.0). A read counts as `premade` when any piece had a clip, so a read that falls back from page 5 on looks like a good one; the fallback reasons are Slice 273's. A lion-and-mouse fa `audio_pack_download` has `started` with no `done` or `failed` today: find out why (item 5).

### Built (2026-11-05)

- **Item 1:** `generate.py --dry-run --batch` on the 8 current dumps said 0 requests for each; the real run (`--batch`, `--max-requests 1`, a dummy key so nothing could be billed) printed "0 rendered, N already had a clip" for all 8: **0 Gemini requests**. Only the 8 `manifest.json` files changed (sound-word entries dropped, renumbered); the dropped sound-word clips stay in the folders unreferenced (a pack ships only the clips its manifest names).
- **Item 2:** `build-audio` raised the six broken packs to v2 (goldilocks, lion-and-mouse, little-red-hen, red-riding-hood, town-mouse-country-mouse, ugly-duckling) and recorded them in `audio-cast.json`; three-little-pigs and tortoise-and-hare rebuild to the same hash and stay v1 (the live packs are already right). How a phone with the old pack gets the new one: `AudioPackStore.InstallAsync` skips only when the installed version equals the listed one, and `ShelfAudioPlan` counts a book as needing a pack when an older version is installed (`StoreClient.WantedPacks` / `BookUpdater.SyncPacksAsync` ask `InstallPacksAsync` for each listed pack, and the cold-start `ShelfAudioPacks.Resume` plans the same way), so v1 on the phone fetches v2 at the next cold start or weekly check; `PublishFolder` then deletes the old version's folder. No version bump by hand: `AudioPacks.Decide` raises the version when the content hash (manifest first) changes. `dino-store.yml` uploads the six on merge (`--audio-behind`: record vs live).
- **Item 3:** `BookBuilder check-audio [<stem>...]` (`AudioAlignment.cs`; unit tests `AudioAlignmentTests`) compares each `audio/<lang>/manifest.json` index and hash with the dump the app reads and prints `<book> <lang>: first bad position N: the manifest holds "..", the app reads ".."; X manifest entries, Y pieces read`. On origin/main's manifests (before item 1): `8 of 240 audio manifest(s) do not line up.` exit 1 (e.g. `lion-and-mouse fa: first bad position 19: the manifest holds "غرررر!", the app reads "ولی شیر یه پادشاه مهربون بود و پنجه‌شو ب..."; 81 manifest entries, 75 pieces read`); after item 1: `All 240 audio manifests line up with the sentences the app reads.` exit 0. CI: a pull-request job `audio-alignment` in `tools-selftests.yml` (ubuntu; only `manifest.json` from LFS) behind a `scope` job that also keeps the Windows self-tests off Core/content changes, paths `src/DinoReader.Core/**`, `src/DinoReader.App/StoryVoicing.cs`, `tools/DinoReader.BookBuilder/**` (already covered by `tools/**`), `content/dino/**`; and the same check as a step in `dino-store.yml` before any pack is built, so a misaligned manifest on main uploads nothing. Run against the live store (item 4) it is not covered: item 4 still needs the live-scan script.
- **Item 5:** In `AudioPackStore.InstallCoreAsync`, `started` is reported before the fetch and every ending reports `done` or `failed:<kind>` except one: a cancel (`PackInstall.Cancelled`, the grown-up's Cancel on the shelf card, a removed language, the book check's token) and a killed or backgrounded app, which end the download without any count. Not a missing count to add here: the Worker accepts only `started`, `done` and `failed:<kind>` (a `cancelled` value needs the Worker's list and `AudioPackUsage` changed together, outside this slice's Touches), and which of cancel or kill happened on that one 2026-11-05 phone cannot be told from the counts. The failure-path reads found no other uncounted ending. Follow-up if wanted: count `cancelled`.
