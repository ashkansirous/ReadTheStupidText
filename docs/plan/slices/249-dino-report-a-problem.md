### Slice 249 — Dino: "Report a problem" in the grown-ups' corner sends the app's recent log, with a code to quote

*Planned (2026-11-02).*

**Touches:** `src/DinoReader.App/SettingsPage.cs`, `src/DinoReader.App/ReportProblem*.cs` (new), `src/DinoReader.App/Resources/Strings/AppResources*.resx` (own block), `src/ReadTheStupidText.Mobile.Shared/Crashes/**`, `src/ReadTheStupidText.Application/Crashes/CrashReport.cs`, `worker/crashes.ts`, `worker/*.test.mjs`, `tools/crashes/pull-crashes.mjs`, `PRIVACY.md`, `site/privacy.html`, `site/dino/privacy.html`, `STORE.md`, `.maestro/dino/**`, `docs/plan/slices/249-dino-report-a-problem.md`

**Why.** The user, 2026-11-02, after the Slice 248 bug: "what would we need if we want to be able to understand this problems based on the data when a user reports it?" A user's report today leads to no data: usage rows have no id and say nothing about playback, and TestFlight sends no usage at all (`UsageGate.cs:121-126`). The user approved this order (2026-11-02, "Im fine with your suggestions. lets plan them"): this slice first, then [Slice 250](250-dino-playback-events-and-session-id.md) (playback events and a session id), then [Slice 251](251-dino-beta-usage-dataset.md) (TestFlight rows in their own dataset).

**What exists (read on origin/main, 2026-11-02).** Release builds keep a rolling log at `<AppData>/crashes/log` (`CrashReporter.cs:18-20, 69`), written only while the crash gate is open (`CrashLog.cs:18`; the gate allows TestFlight, `CrashGate.cs:9`). Every crash report carries its tail (`CrashReport.cs`: `LogTail` up to 32 KB, no identifier) and goes to `POST /api/crash` (`CrashSender.cs:27-28`), stored in R2 at `crashes/<app>/<date>/<random>.json` (`worker/crashes.ts:34, 198-201`, body cap 64 KB, 10 per minute per connection), read by `tools/crashes/pull-crashes.mjs`. Crash reporting is off on Windows (`CrashReporter.cs:49-52`). The lines the log needs to explain a playback bug (page shown or left, Back, reading started/paused/stopped and why, background and foreground) are [Slice 243 item 5](243-crash-report-gaps.md); this slice needs them and builds them first if 243 has not.

#### Work

- [ ] **1. Log lines (prerequisite).** If Slice 243 item 5 is not merged, build it here (Android and iOS, both apps, no user text, `Mobile.Shared/CLAUDE.md:26`) and tick it there.
- [ ] **2. A user report is a crash report of its own kind.** `CrashReport.Kind` gets a `user_report` value (named constant). It carries the log tail, version, platform, channel and coarse device like a crash, no exception or stack. The worker accepts the kind (same caps and rate limit) and stores it under `crashes/<app>/<date>/report-<code>.json`.
- [ ] **3. The reference code.** The app makes a random 8-character code per report (letters and digits without look-alikes: no 0/O, 1/I/L), sends it in the report and shows it. The code identifies that one report and nothing else (not the install, not the person).
- [ ] **4. The row (Android and iOS).** In the grown-ups' corner (`SettingsPage.cs:351`, the `phone` section next to About): "Report a problem". Its page says in plain words what is sent (the app's recent technical log: screens, buttons, reading events; no names, book titles or anything typed) and has one Send button. Sending over 500 ms shows a loading state with Cancel. Then: "Sent. If you write to us, quote this code: K7QX-2MRD", with a Copy button. On failure: say so and keep the report to retry (the crash queue's own retry). Strings in all 15 resx files, in the feature's own block.
- [ ] **5. Finding a report.** `pull-crashes.mjs --code K7QX2MRD` (dash and case ignored) prints that report's fields and log tail; the normal listing shows user reports apart from crashes.
- [ ] **6. Privacy text.** `PRIVACY.md` and both `site/` privacy pages (`worker/CLAUDE.md:10-11`) describe the user-sent report: what it holds, that it is sent only when a grown-up presses Send, and how long it is kept (the crash reports' retention). `STORE.md`: check the Play Data safety and App Store privacy answers against it (crash logs and diagnostics are already declared, `STORE.md:868`, `PrivacyInfo.xcprivacy`); change them only if the new report adds a category. A console change is the user's step, written in Outstanding work.
- [ ] **7. Check.** Unit tests: code alphabet and format, the report's kind and fields, the worker accepting `user_report` and rejecting an unknown kind. Emulator flow: open the grown-ups' corner through the gate hook, Report a problem, Send; assert the code shown matches the logged one (DEBUG marker) and that the worker test endpoint received it (the harnesses' off switch must not drop this one: the flow sets the endpoint to the local test worker, never production).
