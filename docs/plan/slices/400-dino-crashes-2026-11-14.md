## Findings (item 1, read 2026-11-17 from `node tools/crashes/report.mjs -App dino -Since 2026-11-01`; every cause is "likely" until a log or rerun shows it)

- **Android stream close (3b623c4d, 69f96ea0, 1.123.1).** The report's own Java trace says `NetworkOnMainThreadException` inside okhttp `FixedLengthSource.close` -> `Util.discard` -> `skipAll` -> socket read. The managed stack: `FirstBooksPage.BuildBar` tap -> `ContinueAsync` -> `StoreClient.CopyCappedAsync` -> `await using body` -> `GuardedStream.Dispose` -> `inner.Dispose` -> `InputStreamInvoker.Close`. Closing a response body that was not read to its end makes okhttp read the rest on the closing thread; here that thread is the UI thread (the await resumed on it). Likely trigger: the copy left the loop early (cancel, a size-cap or disk error) with bytes unread. **Fix:** the response owns the close (`GuardedResponse.Dispose`; a stream with an owner leaves its close to it). A body that was opened and not read to an explicit end (a read returning 0 into a non-empty buffer) is closed, body first and then the response, by ONE thread-pool task; a finished or never-opened one closes inline as before. The end-of-body flag and that decision live in `BodyCloseState`, shared by `GuardedStream` and `GuardedResponse`. The stall-abandon route uses the same single task. A close that throws is logged (type only) as `PACKDL close-failed`. Debug log lines `PACKDL close-off-thread what=body|response|request` and `close-failed what=... type=...`.
- **iOS twin.** The same shared `GuardedStream`/`GuardedResponse` wrap iOS bodies (`NSUrlSessionHandler`), so the fix covers it with no iOS-specific code (likely, not checked on iOS: iOS has no main-thread network check, and whether an unread-body close there waits on the socket is unconfirmed). The iOS compile and a device check are owed (no Mac here): see *Not yet verified*.
- **iOS scene-update watchdog (658ad15c, 1.131.0, 0x8BADF00D, iPhone 8 class, RAM under 3 GB).** The stored stack is cut at 16384 characters, but the symbolicated copy (`reviews/s243-658ad15c.txt`, dSYM of dino-v1.131.0) shows the main thread inside `-[Microsoft_Maui_Platform_ContentView layoutSubviews]` -> `UIView.set_Bounds` -> Xamarin `objc_msgSendSuper`, under `UIApplicationMain`; no Dino frame, frames printed unique, not ordered. Likely (not proven): a MAUI layout pass that is very heavy or loops (invalidation storm) on a 2 GB phone, not a blocking call in our code. Which page is not shown. I first guessed the cold-start staged-book apply (`GalleryPage.WaitForStagedUpdatesAsync`) and **dropped that change**: managed async code would not sit in `layoutSubviews`. **No fix in this slice.** Needed next: a Debug/Release timing line per layout pass over, say, 500 ms with the page name (a new slice or Slice 243's lane), and a symbolicated stack that keeps the order.

No ANR is in the stored reports or the 2 Play error reports (both are the 1.129.2 store-chip crash, Slice 394 / report 1.129.2 `IllegalStateException`, and a 1.102.0 `AutomationId` crash). `PageImageSize.Read` (header only) and the `.Result` uses in `AndroidSpeechReader`/`AndroidSupertonicSpeechReader` are guarded by `IsCompletedSuccessfully`; none of them is a block of seconds.
