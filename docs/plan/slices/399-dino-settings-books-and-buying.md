#### From review

- Review #1, #2, #3, #6 (`reviews/pr-1250-high.md`) and #1-#9 (`reviews/pr-1250-medium.md`), final design for Restore from Settings: the Store page is the one owner of a restore (its loading state, result message and error); Settings shows no overlay, alert or timeout. Settings' Restore row calls the non-async `StorePage.RequestRestore()` (one pending flag, main thread only) and selects the Store tab. The Store consumes the request exactly once at the end of `Appearing`, after its catalog load ends or when it finds the catalog loaded, and runs the same path as its own Restore link (Slice 396) with its own wait text and messages. A failed load drops the request (the Store's load-failure screen stands, no restore message); `Disappearing` clears nothing else. `RestoreOutcome`, `SettingsBuyingText.RestoreOutcomeLine`, their tests and the extra `_restoring` state are removed; `TryRestoreFromKeyboard` stays. The Maestro flow expects the Store's own message, not a Settings alert. The coordinator widened Touches to `StorePage.xaml.cs` for it. Not yet verified on a device: the request reaches a Store tab that was never opened, and one that is already loaded.
