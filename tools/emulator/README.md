# Warm headless emulator (Slice 161)

One `RTST_Test` x86_64 emulator, no window, fixed port (`emulator-5554`), reused across a wave.

- `start-warm.ps1` boots it (`-no-window -no-boot-anim -no-audio -gpu swiftshader_indirect -memory 4096`), or returns at once if it is already up. Slice 241: a start resumes the AVD's `rtst-clean` snapshot (about 10 s instead of 58 s cold; `start-warm.ps1 -ColdBoot` or `RTST_COLD_BOOT=1` skips it). Slice 162 had turned snapshots off because a resumed one carried stale state and broke Maestro flows, so the snapshot is taken once, right after a cold boot with the dev apps and the Maestro driver uninstalled (a clean machine), and is only loaded (`-no-snapshot-save`: an exit never writes it back). After a resume the `installed-*.key` files are dropped (the restored disk has no dev app), so the next install is a real one; a snapshot that does not boot in 90 s is killed and the boot is cold; a restart after an unhealthy emulator is always cold. NOT yet tried on a device. Boot once per session and keep it running between runs; a second `start-warm.ps1` reuses it. RAM and GPU are flags, so the AVD's `config.ini` is never edited.
- `-NoBuild` (Slice 242; also `RTST_NO_BUILD=1`) on `install-debug.ps1` and `run-flows.ps1`: start no build. On a cache miss they print `cache missed for <app>, key <k>: run install-debug.ps1 -BuildOnly first` and exit 6 (`-App auto` keeps exit 6 when no app failed; any real failure is exit 1). `install-debug.ps1 -Rebuild -NoBuild` is refused with exit 6. Self-test: `test-no-build.ps1` (pwsh and powershell).
- `install-debug.ps1 -App rtst|dino` builds an `android-x64` Debug APK (embedded assemblies), installs and launches it. The x86_64 sherpa-onnx natives are fetched by `src/AndroidSherpaPackaging.props` on first build.
- `stop.ps1` stops only the emulator `start-warm.ps1` started (pid in `<worktrees folder>/.emulator/state.json`, shared by all worktrees; a machine-wide mutex serialises start and stop).

## Slice 180: one build per commit, two emulators, only the touched apps

- `..\test-targets.ps1` prints which of `rtst-android`, `rtst-windows`, `dino-android`, `dino-windows` a change needs (CI's own file mapping, `ship-targets.mjs --local`, plus the test tooling's files; a tooling file it cannot place runs everything). `run-flows.ps1 -App auto` runs only those and lists the skipped ones.
- `install-debug.ps1` builds the APK once per **build key** (hash of `src/` and the root build files as on disk) into `<worktrees folder>/_builds/<app>-android-<key>/` and reuses it (any agent, any worktree); `-Rebuild` forces a build; the emulator boots while the build runs. The newest 3 builds per app and worktree are kept. `build-cache.ps1` holds the key logic.
- Two emulators: `new-avd.ps1` creates `RTST_Test2` by copying only `config.ini` (it does not copy RTST_Test's 16 GB disk; the emulator makes small disk files on first boot, which took 101 s under load); every script takes `-Instance 1|2|3|tablet` (`emulator-5554` / `emulator-5556`; `3` or `tablet` is the tablet AVD `RTST_Tablet` on `emulator-5558`, made by `new-avd.ps1 -Tablet`, Slice 242; own state file and lock); `start-warm.ps1 -Instance any` takes a free one and prints which. A running instance counts as taken: stop it (`stop.ps1 -Instance n`) when done. Maestro output is per instance.
- `activity.ps1`: builds, flows runs and VM runs register while they run; `tools/phone/audio-timing.ps1` takes the quiet-machine lock first, waits for them to end, and holds new ones off until it finishes.

Always address it with `adb -s emulator-5554`; a real phone may also be connected.
- **Load limit** (measured 2026-10-28, i9-11950H, 32 GB): one emulator + the VM is fine; two emulators with flows and no VM is fine (2/2 each); **two emulators + the VM is too much** (CPU 100%, RAM 30.7 of 32 GB: one flows run and all three VM checks failed). `activity.ps1` enforces it: a VM run waits (and prints why) while two emulators run flows, and a second emulator's flows wait while the VM runs. Never start a flows run while the other emulator is still booting (Maestro: "Device emulator-5554 was requested, but it is not connected").
- **One emulator runs flows at a time by default** (Slice 207): `Get-ConcurrencyConflict` now makes a second emulator's flows wait while another emulator runs flows (the VM may still run beside one). `RTST_ALLOW_TWO_EMULATORS=1` restores the two-emulator limit above (and still keeps the VM off while two run flows).
- **Emulator lease** (Slice 207): `run-flows.ps1` takes `<worktrees folder>/.emulator/lease-<adb serial>.json` (shared code in `tools/lease-common.ps1`, which the phone lease uses too) after the APK is built or found in the cache (a cold build holds no lease) and right before the install, so a second run on the same serial cannot `clearState` the first one's data. Owner: `$env:RTST_DEVICE_OWNER`, else `$env:RTST_PHONE_OWNER`, else `run-flows-<pid>`. Expiry 30 min, renewed between flows, and a run that finds another owner holding it stops with exit 4; a lease whose owner process is gone, or that expired, is free. A held lease makes the second run print `LEASE waiting on <owner>` once a minute for up to `-LeaseWaitMinutes` (default 15), then exit 4 naming the holder. `tools/phone/audio-timing.ps1 -Emulator` takes the same lease. Self-test: `test-lease.ps1` (pwsh and powershell).
- **Emulator health before every flow** (Slice 215): `run-flows.ps1` checks `adb shell pm path android` (must answer) and `getprop sys.boot_completed` (must be 1) before each flow and after a failed one. If not it prints `EMULATOR UNHEALTHY (<when>): <what>`, saves `logcat -b crash -d`, `dumpsys meminfo`, the host's free RAM and the qemu working set under `<worktrees>/.tools/maestro-out/i<n>/unhealthy-*`, restarts the emulator from the shared `.emulator` folder (never from inside a worktree) and runs the flow once more. The second unhealthy check of a run exits 5 naming it, so a dead `system_server` (2026-10-30: `pm` gone while `sys.boot_completed` stayed 1) is never read as an app failure. Self-test: `test-activity.ps1` (pure parts, pwsh and powershell; also the one-emulator limit); `test-activity.ps1 -DeviceKillCheck` is the scripted emulator check (kills `system_server` with `adb shell su 0 kill`, expects the health check to see it, waits for recovery).
- **Flow lint** (Slice 215): a `runFlow` file is followed and its `launchApp` lines judged as if inlined; the inline `launchApp: {...}` form is tokenized (quotes, nested braces); the `# clearState:` comment may sit above the key or above its `- launchApp:` item and quoted text is ignored; `stopApp: true` counts as a restart; a flow with doubled CRs or mixed line endings fails.
- **Flow lint** (Slice 207): `lint-flows.ps1 [-Path .maestro]` checks the flow text with no device (exit 1, `file:line: message`): every command name is a Maestro command (also inside `runFlow`/`repeat`/`retry` `commands:`), no bad escape such as `\+` in a double-quoted string, every `clearState` has a `# clearState:` comment above saying what it wipes and why that is fine, and `appId` is a dev package. `run-flows.ps1` runs it first and stops before any build when it fails; `test-lint-flows.ps1` checks each rule against `fixtures/lint/`, and runs in CI with the other tool self-tests (`.github/workflows/tools-selftests.yml`, Slice 212). **Per-flow setup** (Slice 212): before every flow `run-flows.ps1` sends `KEYCODE_WAKEUP` and `wm dismiss-keyguard` (a warm emulator sits on the lock screen). A flow whose header carries `# needs: cellular-only` runs with Wi-Fi off and mobile data on (`svc wifi disable`; `svc data enable` if data was off), and Wi-Fi is switched back on after it in a `finally`, so a failed flow never leaves it off. `lint-flows.ps1` rejects any other `needs` value. A `launchApp` that sends a hook (`arguments` with `cmd`) after the flow's first one needs `stopApp: false` (the hook reaches the running app as a new intent) or a `# launchApp-restart:` comment saying why a restart is wanted.
- **Builds run at BelowNormal priority** (`Set-BuildPriority`; dotnet and msbuild children inherit it), because flows failed 0/2 while an MSIX build held the CPU at 100%.
- **System UI "isn't responding"**: `run-flows.ps1` looks for an ANR dialog before and after the flows, taps *Wait* (or *Close app*) and prints that it did; if it cannot clear it, it fails naming the dialog. Before this, one ANR failed every later run until the emulator restarted.
- `-Instance 2` works in every script (the chosen number is `$script:EmuInstance`; it used to overwrite the caller's `$Instance`). Each flows run gets its own Maestro `user.home` per instance.

## Slice 241: device-test speed (docs/plan/slices/241-device-test-speed.md)

- **Fail fast:** after a failed flow `run-flows.ps1` reads the crash buffer and the ActivityManager ANR lines for the app (`Find-AppCrashLines`, `speed.ps1`). A crash or ANR stops the rest of that emulator's flows: each prints `NOTRUN <flow> (app crashed in <flow>)`, the summary counts them and the exit is 1. (Not built: killing a running Maestro flow the moment the crash appears; the first flow still waits out its own timeouts.)
- **Build during boot:** on a cache miss `run-flows.ps1` starts `start-warm.ps1` detached (log `<worktrees>/.emulator/boot-<n>.log`) and builds meanwhile, then waits for both before the install.
- **One call, one emulator (two on request):** `-Flow a,b,c` names several flows; no `-Flow` runs them all. By default they all run on emulator 1 (Slice 207's limit: two emulators overloaded the PC). With `-Split` (or `RTST_SPLIT=1`) and 4 or more flows the second half runs on emulator 2 at the same time; emulator 2 gets 180 s to boot, after that its flows run on emulator 1 (`RTST_ALLOW_TWO_EMULATORS=1` is set for the run, `new-avd.ps1` creates the AVD when missing, the boot overlaps the install, and `stop.ps1 -Instance 2` runs at the end). The child's output is `<worktrees>/.emulator/split-i2.log`, echoed with an `[i2]` prefix. Never with the VM running two emulators (the activity limit still applies).
- Self-tests: `test-speed.ps1` (pure parts) and `tools/test-detached-process.ps1`, in pwsh and powershell.
